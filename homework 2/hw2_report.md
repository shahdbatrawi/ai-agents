*Dashed = not finished at the time of writing (update to match the final code).*

- **Startup / data (changed from HW1):** the app no longer rebuilds the database on every start. A `meta` table holds a `Seeded` marker, written only after all four resume tables are loaded. `llm_roles` is reloaded on every start because it is system configuration, not user data.
- **Embeddings (new):** each record in `institutions`, `positions`, `experiences` and `skills` gets a text, an embedding from the API, and a row in the `embeddings` table (JSON vector, the embedded text, the model name).
- **Search by meaning (new):** the query is embedded, compared to the stored vectors with cosine similarity in plain Python, and ranked.
- **Experts (HW1, unchanged so far):** Orchestrator, Read, Write and Content Experts as in HW1.
- **Routing:** the Orchestrator's plan has a `role`, a `message` and a `reason` per step. Exact questions (counts, lists) go to the Read Expert; fuzzy ones (abbreviations, categories) go to search by meaning.

**What surprised me**

- **The same request gave different results** (T3, T5, T6). I traced T3, T4 and T5 to the Write Expert's own prompt in `llm_roles.csv`: it only teaches `insertRows`, it allows only two outcome messages ("added" or "already exists"), so a delete request has no valid answer. ## 5. Limitations

1. **Limitation:** the read path still depends on SQL written by the model, with only a check that the text starts with `SELECT`. **Impact:** answers can change with the wording (T6). **How I'd improve it:** route common question shapes to fixed, parameterized queries, open the read connection as read-only, and keep a regression test that asks the same question several ways.
2. **Limitation:** every search loads all stored vectors into Python, and the cut-off score was calibrated on about 30 records and one model. **Impact:** fine at this size, but slow on large data, and scores can shift if the data or model changes. **How I'd improve it:** cache vectors in memory or use a vector index, and re-calibrate the cut-off whenever `EMBEDDING_MODEL` changes (the stored model name makes the change detectable).

 **3.Limitation:** create_and_store_embeddings() re-embeds every record on each call, does   not update the model column when a row already exists, and does not delete the embedding of a deleted record. Search also returns "No matching records were found" when the embeddings table is empty. Impact: extra API calls and cost on every run, stale model values after a model change, orphan rows that can still match a search, and an empty index that looks like "no match". How I'd improve it: a sync step that embeds only records that are missing or whose text or model changed, removes orphans, uses one database connection, and reports "search index is empty" separately from "no match".
